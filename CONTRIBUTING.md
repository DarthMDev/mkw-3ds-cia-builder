# Contributing to Mario Kart Wii (3DS)

Thank you for contributing to the Mario Kart Wii 3DS port! 

This project aims to preserve, optimize, and expand the native 3DS port of Mario Kart Wii. To maintain high code quality, system stability, and deterministic gameplay across all 3DS hardware revisions, please follow these guidelines.

---

## Code Philosophy & Clean Code Guidelines

This is a high-performance native engine targeting the Nintendo 3DS (ARM11 CPU and PICA200 GPU). Clean, readable, and hardware-conscious code is essential.

### C++ Standards
- **Standard**: C++23 (`-std=gnu++23`).
- **No Exceptions or RTTI**: Code is built with `-fno-exceptions` and `-fno-rtti`. Use error codes, status enums, or `std::optional` / `std::expected` patterns instead.
- **Floating-Point Determinism**: Physics calculations rely on Kinoko's deterministic simulation (`-ffp-contract=off`). Never introduce compiler flags or math shortcuts that violate IEEE 754 precision or alter physics calculations.

### Memory & 3DS Hardware Constraints
- **Heap Separation**: 
  - **LINEAR Heap** (`linearAlloc`, `linearMemAlign`): Reserved strictly for GPU-accessible data (textures, vertex buffers, display lists, particle buffers, audio stream rings). On Old 3DS (64 MB total RAM), the linear heap is capped at **32 MiB**.
  - **Application Heap**: Used for general engine logic, game objects, and Kinoko's physics arena.
  - Linear allocations in multi-threaded contexts must respect the thread-safe linear locking wrappers in `src/linear_lock.cpp`.
- **Target Both Old & New 3DS**:
  - Always keep the Old 3DS memory budget (64 MB) in mind. A feature that works on Citra or New 3DS will crash on an Old 3DS if it exceeds the heap limit.
  - Old 3DS targets 30 FPS; New 3DS targets 60 FPS (or 30 FPS in stereoscopic 3D mode).
- **Code Style & Structure**:
  - Match existing codebase conventions: `CamelCase` for classes and structs, `camelCase` for functions and variables, and `UPPER_SNAKE_CASE` for constants.
  - Avoid unnecessary external dependencies or heavy templates that bloat binary size or executable cache lines.
  - Document hardware-specific workarounds (e.g., PICA200 register quirks, cache flush operations, DSP audio DMA).

## AI Usage Policy

AI coding assistants (Claude, ChatGPT, GitHub Copilot, Gemini, etc.) **are permitted**, but subject to the following rules:

- **You Are Responsible for Your Code**: 
   Any code generated by an AI assistant must be thoroughly read, understood, and vetted by you before opening a pull request.
- **No Hallucinations or Fictitious APIs**:
   LLMs frequently hallucinate CTR/libctru syscalls, Citro3D functions, or Kinoko classes. Double-check all functions and types against actual headers (`include/mkw/`, `vendor/kinoko/include/`, `devkitPro/libctru`).
-  **No Unreviewed Bloat**:
   Do not submit large dumps of unreviewed AI code. Submissions that exhibit obvious hallucinated logic or disregard the project's memory model will be closed.
- **Mandatory Testing**:
   AI-generated changes must be compiled and tested on an emulator or real 3DS hardware. If you haven't run and verified the code yourself, do not submit it.

## Testing Your Code

Before submitting any changes, you must verify both compilation and runtime behavior.

### A. Local Build Verification
Ensure the project compiles without warnings or errors:

```bash
# Verify normal build
python3 tools/build.py

# Verify release build (optimizations and LTO enabled)
python3 tools/build.py --release
```

If you made changes to the asset pipeline (cookers, parsers, or Python scripts), verify with:
```bash
# Verify that all asset tools pass validation against an extracted disc
python3 tools/release/build_cia.py --check
```

### B. Runtime Testing
- **Emulator Testing**:
   - Test using an accurate 3DS emulator.
   - Check that courses load, camera angles operate correctly, bottom-screen UI and touch controls respond, and audio streams cleanly without buffer underruns.
- **Real Hardware (Highly Recommended)**:
   - If you have access to a modded 3DS, build the CIA (`build/release/mkw-3ds.cia`), install it via FBI, and test on actual hardware.
   - Verify performance and stability across:
     - Course intro cutscene & race start.
     - A full 3-lap race with 12 racers.
     - Race finish and results flow.
     - Repeated race restarts (to catch memory leaks).
     - HOME Menu suspension and resume.

## Legal & Cleanroom Policy

- **NEVER commit raw game data, ISOs, WBFS dumps, or extracted proprietary Nintendo assets.**
- All game files (models, music, course archives) must be cooked at build time by the player from their own legally dumped disc.
- Keep all submodules pinned to clean, public open-source repositories as defined in `dependencies.json` and `.gitmodules`.

---

## Pull Request Guidelines

- **One Focus per Pull Request**: Keep PRs focused on a single bug fix, feature, or optimization.
- **Clear Descriptions**:
   - Explain the problem your PR solves.
   - Describe what testing was conducted (e.g. *"Tested in Lime3DS and on a New 3DS running Luma3DS v13.0"*).
   - Note any performance or memory impacts.
- **Clean Git History**:
   - Ensure your commits are logical and well-described.
   - Rebase on the latest `main` branch before submitting.
